- Evidence: `git ls-files crates/ajax-web/src/runtime/state.rs crates/ajax-web/src/slices/web_session/session_evidence.rs crates/ajax-web/src/slices/web_session/task_session_directory.rs | xargs wc -l` returned `993`, `292`, `994` (2,279 total). `rg -n 'report_or_defer_task_session_activity|deferred_activity_pending|live_overlay|record_session_activity' crates/ajax-web/src/runtime crates/ajax-web/src/slices/web_session --glob '!**/*test*'` returned runtime `state.rs:404` recording activity, `:518` wiring reporting, `:521` wiring pending detection; cockpit `:101,:227,:365` reading the live overlay; directory `:122` building it; task actor `:443` checking pending reports. These are live paths, not dead modules.
- Duplicate fact and owners: current chat activity lives in `SessionEvidence.activity_reporter`, directory `live_entries`, and `WebSharedState.context.registry` (then its durable snapshot). Delivery also appears in `SessionEvidence.pending_activity_report` and runtime `DeferredActivityReports`. The former holds a failed callback; the latter holds accepted but lane-blocked reports, so they are different delivery stages.
- What keeps them in sync: `SessionEvidence::report` publishes the directory slot before calling the reporter, commits local reporter state on acceptance, and retains failed reports. Runtime `report_or_defer_task_session_activity` preserves arrival order; its drainer applies registry mutations under the control lane. `record_task_session_activity_under_lane` retries after reload and calls `applied_live_activity`; that removes the overlay only when activity matches. Cockpit overlays a cloned registry context while delivery is pending. This machinery exists specifically to reconcile the copies.
- What replaces it: use live activity as the turn-state authority and a deliberately designed durable cold-read/push projection. Retain core observation reduction and process evidence. Do not simply delete callbacks: directory recovery and actor eviction depend on delivery completion.
- Behavior or public contract change: **NEEDS APPROVAL — ownership/lifecycle architecture change. PUBLIC documented behavior:** `architecture.md:167–174` explicitly retains registry activity snapshots, the deferred queue and client convergence until Matt signs off on the pinned test contracts. Removing them immediately would alter push/cold-read status and recovery. No HTTP route deletion proposed.
- Risk: **high**; lost ordering can publish an old running state after turn end, and losing the durable projection changes restart behavior.
- Depends on: explicit Chat-first approval and replacement of registry-only push/cold-read consumers. Independent of B2 harness consolidation and legacy import.
- Confidence: **speculative** for net removal; duplicate owners, callers and gross 197-line reconciliation budget are proven.

- Evidence: `rg -n 'restore_queued_prompts|QueuedPrompt|apply_cancel_to_queue' crates/ajax-web/src/slices/web_session/{task_session_exit,task_session_adopt,task_session_spawn}.rs` returned exit `:315,:326,:344,:449,:520,:687`, adopt `:17,:103`, spawn `:13,:287,:356`. `git ls-files` of the named files piped to `xargs wc -l` measured exit 773, mod 523, queue 74, adopt 293; ledger baseline is 631 from B2, not counted again. `nl -ba .../task_session_exit.rs` confirmed the exact ranges above.
- Duplicate fact and owners: `PromptLedger.entries` stores client ID, phase, transcript text, prompt text and JSON content blocks. `PromptQueue.queued: VecDeque<QueuedPrompt>` duplicates client ID/text/blocks, plus prebuilt ACP blocks. `TranscriptLog` separately retains the displayed user message under `u:<client_message_id>`; it is history, not queue membership. Completed ledger entries clear their text/content, while transcript history survives.
- Synchronization: admission commits ledger plus user event before pushing the queue; updates persist the ledger, mutate the queued payload, then append the replacement user event; withdrawal removes ledger then queue entry; cancel removes queued ledger entries before clearing the deque; recovery/adoption reconstruct the deque from Queued ledger entries. Dispatch persists Dispatching and shim/transcript positions before sending, and pops the deque only after the dispatch result. `ActivePrompt` retains pending terminal events until durable completion succeeds.
- What replaces it: iterate queued ledger entries in order and build transport payload only for dispatch. Retain the active transport request ID, cancellation acknowledgement, terminal retry buffer, atomic prompt/event commit, and ownership fence. They are not duplicate durable queue facts.
- Behavior or public contract change: **NEEDS APPROVAL if ownership/admission changes.** Empty client IDs currently bypass durable ledger insertion but can enter the deque (`submit_prompt` branches at exit `:433,:457`). A ledger-only queue must preserve that compatibility or explicitly remove it; the latter is a **PUBLIC wire behavior change**. Payload preparation timing also affects errors when capabilities change. `QueuedPrompt` is exported Rust API; external consumers were not disproved.
- Risk: high without handling anonymous prompts, exact-once dispatch, FIFO and retry ordering. The proposed collapse is plausible but cannot honestly be sold as hundreds of lines removed.
- Depends on: a decision about empty IDs and preserved capability validation; independent of B3-01.
- Confidence: **speculative** for net savings; duplication and synchronization paths are proven. Excluded from savings totals because no >=150-line net family was established.
